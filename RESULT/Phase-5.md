# Phase 5 — Bounded adaptation and change monitoring

**Phase 5 gate: PASS (2026-10-07).** The repository now has a deterministic WMC configuration-search harness, development-partition checks, a streaming change detector, versioned in-process audit events, and fail-closed baseline rollback. The complete Phase 5 contract is in [SPEC/components/03-evolution-adaptation.md](../SPEC/components/03-evolution-adaptation.md).

## What changed

The harness owns exactly one mutable setting in `xai_wmc`: `SolverOptions::node_limit`. Its allowed grid is `{1, 2, 4, 8, 16, 32, 64, 128}`, with 128 as the named harness baseline (`wmc-node-limit-baseline-v1`). It exhaustively tests the grid on development-labeled cases, first maximizing exact completions and then choosing the smallest cap tied at that completion count. Successful counts and satisfiability must match the supplied exact oracle; resource-limit outcomes count only as noncompletions and never return partial counts. Other solver settings stay fixed. New API, implementation, CMake target, and tests are in `include/xai/adaptation.hpp`, `src/adaptation.cpp`, `CMakeLists.txt`, and `TESTS/cpp/adaptation_tests.cpp`.

The search preflights suite and record partitions before scoring formulas, rejects duplicate observation IDs and invalid oracle records, and exposes each candidate’s cap, completion count, denominator, successful recursive-node total, and mean log-node count. The baseline candidate’s mean also supplies the detector reference. Version changes and state transitions are appended to an in-memory audit log. A regression, exact-oracle mismatch, monitored solve failure, invalid monitored resource count, or CUSUM alarm freezes exploration and selects the named baseline. A reset is permitted only after the configured streaming hold-off has elapsed and always restarts from baseline.

The monitor uses the residual `log(1 + observed recursive nodes) - mean baseline log(1 + recursive nodes)`, evaluated at its configured cadence. It applies a one-sided Gaussian log-likelihood-ratio CUSUM with explicit in-control/shift means, shared standard deviation, threshold, and hold-off. Alarm behavior and reset are exercised by fixtures; no false-alarm rate or detection-delay guarantee is claimed because these depend on the residual-distribution assumptions, and adaptation itself can change or censor residuals.

## Verification

A fresh GCC 13.3.0 / CMake 3.28.3 Release build completed with strict warnings treated as errors; CTest passed **7/7** targets. The dedicated adaptation executable passed **5/5** groups covering the finite bounds and candidate ranking, development-only scoring and held-out rejection, duplicate-ID checks, exact-oracle validation, deterministic replay and audit records, objective-regression and invariant rollback, streaming failure, CUSUM cadence and shift alarm, hold-off, reset, and recovery. A separate fresh Debug AddressSanitizer/UndefinedBehaviorSanitizer build also passed CTest **7/7** with leak detection enabled and no sanitizer findings. `git diff --check` passed. Exact commands and results are recorded in [TESTS/validation.log](../TESTS/validation.log).

These results establish finite software behavior on small synthetic formulas and signals only. The 98-instance Phase 0 public development benchmark was not used to tune this harness, and no odd-indexed final-test body was opened. Partition labels are caller-supplied rather than authenticated, so the in-process rejection checks do not prove that an external caller has not mislabeled or leaked held-out information. No benchmark utility, solver performance, empirical shift-detection quality, false-alarm guarantee, or system-wide stability claim is made.
