# Component 7 — Supported input and end-to-end orchestration

## Supported route and task mapping

Phase 8 accepts a caller-provided `StructuredWmcInput` containing **unprojected DIMACS weighted CNF**. The in-process parser is `xai-dimacs-wmc-parser-v1`; the solver is `xai-exact-wmc-dpll-v1`. This is a typed syntax route, not natural-language understanding, OCR, archive ingestion, or an entity-resolution service. Unsupported or projected syntax is rejected; it is never repaired into a different task.

The caller must label an input as partition `development` with partition ID `mcc24-public-even`. The runtime checks that boundary before it hashes or parses the formula body, and rejects final-test, streaming, unknown, or differently named partitions on this route. Parser failures retain their explicit status, but raw offending tokens are removed from the run diagnostic and serialized result. **These labels are caller-supplied, not authenticated.** The harness does not read the Phase 0 archive or determine whether a record is genuinely public or eligible. Archive selection and task-specific evaluation remain separate work.

The original input reference, source and observation IDs, timestamp, producer/extractor version, partition labels, formula byte count, and formula SHA-256 are retained in the manifest. The fixed parser version is recorded separately from the caller’s extractor version. Identity bindings retain their formal variable index, resolution state, resolved ID, and candidate IDs. A required unresolved identity fails closed; the runtime does not choose a candidate. Stable uncertainty codes and rejected-span references are retained by identifier only; any caller-declared rejected span blocks partial task mapping. Supplemental identity, evidence, query, and annotation input receives its own canonical SHA-256, without copying formula bytes into the report.

Optional factual evidence is passed through the existing provenance-bearing ingestion contract. Missing facts remain `unknown`, contradictions remain `inconsistent`, and unknown/correlated dependence is not treated as independence. If a requested fact/evidence model exceeds the finite-ingestion cap, the run fails or the factual-ingestion stage is explicitly skipped only when no query/evidence depends on it; raw WMC does not inherit a fabricated factual answer.

## Orchestration and result policy

Each invocation creates fresh in-process state. It does not restore or reuse persisted model, learning, calibration, or adaptation state. Module and data-partition boundaries are checked at entry, and every executed, skipped, or failed stage is recorded with a status and reason. The ordinary route records predictive learning, generic finite reasoning, and calibration as skipped: this unlabeled exact-WMC task supplies neither an authorized learning update nor a calibration split, and its typed CNF is handled by the exact solver.

Adaptation is optional. When configured, its optimizer receives only a development suite and its monitor only streaming observations. The controller audit is retained, and the solver uses the controller’s post-monitor active limit—including its baseline limit after a shift/invariant rollback. The result decision then sees the alarm status and abstains. A missing or invalid required certificate, a verifier mismatch, an upstream failure, or a resource overrun also excludes the exact-result action. **On abstention or invalid decision input, the exact-count and satisfiability fields are withheld**, even if the internal solver stage completed; the trace and resource record show that the solver ran, while the decision object records why no answer was emitted.

A selected `wmc.emit_exact_result` action requires property `xai.wmc.exact-rational-result.v1` and a configured verifier that accepts the formula digest and canonical exact-result digest. Tests use a synthetic fixture verifier only. There is no production proof-certificate format, input resolver, or independent exact-WMC proof verifier, so a fixture-selected result is not evidence that a real benchmark result has been certified.

## Run manifest and replay

The canonical output carries versioned input, run, and outer-output schema IDs/fingerprints; source-content build SHA-256; formula-data SHA-256; supplemental-input SHA-256; factual-model SHA-256 where one was constructed; configuration SHA-256; run/observation/source/partition IDs; original reference; parser, extractor, solver, compiler, build, and verifier versions; optional seed; parser/solver limits; CPU and memory budgets; module trace; adaptation audit; wall time; process CPU time; process peak RSS; and a semantic-result SHA-256. The build fingerprint is generated by CMake from `CMakeLists.txt`, tracked `include/xai/*.hpp`, and `src/*.cpp` contents. Configuration fingerprints include solver/decision settings and any development adaptation suite and detector settings.

The semantic replay digest includes stable statuses, selected result or abstention, data/model/configuration fingerprints, module reasons, identity/uncertainty/rejected-span annotations, and adaptation transitions. Timing, CPU, and RSS measurements are deliberately excluded because they vary by host and run. Adaptation configuration and audit doubles are represented by their exact IEEE-754 bit patterns; no rounded metric is used as a replay key. No Phase 8 module is stochastic; a supplied seed is recorded but is not consumed by this route.

`process_cpu_ms` and peak RSS use Linux `getrusage` where available. Peak RSS is a process high-water mark, not an isolated per-run delta. On platforms where these measurements are unavailable, resource admission fails closed rather than assuming the budgets were met. The solver wall-time limit is clamped to the declared CPU-budget value, but parser/adaptation work is not preempted by an OS-level process watchdog; measured whole-run CPU/RSS can still make the decision gate abstain. The memory budget is an admission limit, not an operating-system memory kill switch.

## Verification scope and limits

The deterministic end-to-end fixtures cover successful mapped input, partition rejection before formula access, missing/contradictory/correlated evidence, ambiguous identity, rejected or unsupported content, solver timeout, adaptation shift rollback, calibration skip rationale, certificate rejection/missing verifier, custom memory-budget rejection, SHA-256 vectors, and deterministic semantic replay. These are in-process synthetic software checks. They do not measure benchmark completion, accuracy, calibration, performance, general language understanding, production proof soundness, or deployment safety. During Phase 8, no odd-indexed formula body was opened. The later Phase 9 cross-split leakage audit did decompress odd-indexed formulas for its predeclared checks; no final-odd formula was solver-scored or used for tuning, as documented in [`RESULT/Phase-9.md`](../../RESULT/Phase-9.md).
